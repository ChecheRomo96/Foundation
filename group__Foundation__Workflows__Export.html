Build and install a clean, target-specific distribution package.

Export configures the target preset once, builds the installable Release artifacts, removes the default dist/<preset> destination, and installs one fresh Release package. The library is always included. Executable API examples are opt-in through --examples-on in Bash or -ExamplesOn in PowerShell.

The exact default sequence is:

  1. configure or refresh build/<preset>;
  2. build FoundationExportArtifacts for Release, including optional examples;
  3. safely remove the repository-owned dist/<preset> directory;
  4. install Release into that directory.

Debug remains available through the build and test workflows but is not part of the distribution package.

Bash

./scripts/export.sh <preset> [--output <path>] \
[--parallel <jobs>] [--fresh] [--keep] [--examples-on] \
[-- <cmake arguments>]
./scripts/export.sh macos_arm64 --parallel 8
./scripts/export.sh psoc5lp_armgcc_cortex_m3_soft
./scripts/export.sh atmega328p_avrgcc_avr5 --fresh
./scripts/export.sh macos_arm64 -- -DFOUNDATION_SCHEDULING=OFF
./scripts/export.sh macos_arm64 --fresh --examples-on

Examples for PowerShell:

./scripts/export.ps1 windows_msvc_x64 -Fresh -Parallel 8
./scripts/export.ps1 windows_msvc_x64 `
-CMakeArguments "-DFOUNDATION_SCHEDULING=OFF"
./scripts/export.ps1 windows_msvc_x64 -Fresh -ExamplesOn

Arguments and Defaults

Argument Default Meaning
configuration Release Fixed distribution configuration.
output dist/<preset> Installation prefix for the package.
parallel CMake default Worker count for each build.
fresh off Clears CMake cache state before the single configure.
keep off Preserves and overlays the destination.
examples off Builds and installs Release API examples.
CMake arguments none Cache overrides applied to the Release build.

PowerShell

./scripts/export.ps1 <preset> [-Output <path>] `
[-Parallel <jobs>] [-Fresh] [-Keep] [-ExamplesOn] `
[-CMakeArguments <arguments>]

Export has no configuration selector: distribution artifacts are always Release. CMake arguments customize the single configure/build operation.

--examples-on and -ExamplesOn set FOUNDATION_EXAMPLES=ON for that configure operation. Without the switch, the preset default remains OFF, so regular packages contain only the library, public headers, and CMake package metadata. Exported examples are Release-only; Debug examples can still be built from the source tree when needed for development.

A custom output path requires --keep or -Keep. This prevents the export workflow from recursively deleting an arbitrary caller-supplied directory. In keep mode, installation overlays the destination.

Warning
Keep mode can retain files from an older feature selection. For a reproducible custom package, choose a new empty output directory or explicitly clean that caller-owned directory before invoking export. The default dist/<preset> path is the only destination the script deletes automatically.

The legal notice, package overview, and version history are installed at the package root so they remain adjacent to every redistributed binary. Windows uses Foundation.lib rather than the Unix archive name, appends .exe to example executables, and installs the single FoundationExamples.cmd menu launcher. Only Release examples are distribution artifacts. Headers are configuration-independent and installed once. FoundationTargets-release.cmake maps the imported target to the Release archive.

The macOS .command and Windows .cmd launchers are console menus intended for double-click use. Each discovers the adjacent examples, runs the selected executable, displays its exit code, and asks whether to run another. Pressing Enter or answering y returns to the menu; answering n or q exits. Terminal owns the macOS window after the script exits; select Terminal > Settings > Profiles > Shell > When the shell exits to choose whether a successful launcher closes it. Launchers are installed only when examples are enabled; they are not CTest tests or replacements for the executable artifacts.

FoundationBuildInfo.cmake records the exported version, platform, system, processor, macOS architecture, compiler, C++ standard, package configuration, ARM CPU/ABI/FPU, and AVR MCU/architecture values, whether executable examples were included, plus the enabled top-level modules. Consumers can load the target with:

find_package(Foundation 1.0 CONFIG REQUIRED)
target_link_libraries(MyApplication PRIVATE Foundation::Foundation)

The consumer should set CMAKE_PREFIX_PATH to dist/<preset> or set Foundation_DIR to its lib/cmake/Foundation directory. It must use a compatible compiler, target architecture, ABI, runtime, and Release configuration. Debug consumers should build Foundation from source. Do not bypass the imported target by guessing a library filename.

Feature Variants

Module overrides are valid because export forwards them into the one configure operation:

./scripts/export.sh macos_arm64 --fresh -- \
-DFOUNDATION_FULL_BUILD=OFF \
-DFOUNDATION_SCHEDULING=OFF \
-DFOUNDATION_CONTAINERS=OFF

The generated FoundationBuildInfo.cmake records the enabled top-level modules. A consumer must compile with the exported target's propagated macros and headers. Do not merge packages produced with incompatible feature sets.

Examples remain demonstrations of the public API, not tests. Export does not register them with CTest or interpret their execution as test evidence.

Compatibility Rule

Precompiled libraries are not universal. Produce a separate export for every operating system, compiler/toolchain, architecture, ABI, and incompatible feature set. Every exported package is Release-only. “Any platform” means any target represented by a valid CMake preset and, when cross-compiling, an appropriate toolchain file.

Verification

Before publishing, verify file presence, inspect object architecture with the target tool (lipo, dumpbin, llvm-readobj, arm-none-eabi-objdump, or avr-objdump), inspect FoundationBuildInfo.cmake, and compile an external find_package consumer. See Validation for the complete target matrix.
