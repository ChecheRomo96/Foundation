Build a testing preset and execute its CTest suite.

The test workflow performs three operations in order:

  1. configures the selected preset with FOUNDATION_TESTING=ON;
  2. builds the selected configuration;
  3. runs CTest from build/<preset> with failure output enabled.

FOUNDATION_TESTING=ON is present in the active cache immediately after this workflow. A later script configuration reapplies preset-defined defaults, but a fresh export is still recommended for release packaging because unrelated feature overrides may remain cached.

Bash

./scripts/test.sh <preset> [--config <name>] \
[--parallel <jobs>] [--filter <regex>] [--fresh] [--allow-no-tests]
./scripts/test.sh macos_arm64 --config Debug --parallel 8
./scripts/test.sh macos_arm64 --filter TimePoint

Arguments and Defaults

Test defaults to Debug. The filter is forwarded as CTest's regular expression, parallel controls both compilation and CTest workers, and fresh recreates the cache before enabling testing. Test failures propagate as a nonzero script exit status.

PowerShell

./scripts/test.ps1 <preset> [-Configuration <name>] `
[-Parallel <jobs>] [-Filter <regex>] [-Fresh] [-AllowNoTests]

Test output is always displayed on failure. An empty CTest suite is an error by default so a release cannot silently pass without validation. --allow-no-tests or -AllowNoTests exists only for diagnosing a deliberate configuration that registers no tests and must not be used by a release gate. The test workflow enables only FOUNDATION_TESTING while configuring the selected target preset; a separate testing preset is not needed. Examples are API demonstrations and are never enabled, executed, or reported as tests by this workflow.

Registered Native Suite

The default feature set builds seven module-scoped GoogleTest executables:

  • FoundationMathTests;
  • FoundationTypeTraitsTests;
  • FoundationUtilsTests;
  • FoundationContainersTests;
  • FoundationFunctionalTests;
  • FoundationTimeTests;
  • FoundationSchedulingTests.

gtest_discover_tests() exposes every TEST() case separately to CTest. Each executable uses Foundation's public headers, lives below the matching tests/Foundation/<module> directory, and is registered only when all modules it requires are enabled. Use --filter <regex> or -Filter <regex> to select discovered cases by name without changing the build graph.

GoogleTest Dependency

cmake/BuildTests.cmake obtains GoogleTest 1.18.0 through CMake FetchContent, pinned to the release commit rather than a moving branch. A clean first configuration therefore needs access to GitHub unless the dependency has already been populated or a standard FetchContent source override is supplied. GoogleTest and GoogleMock installation are disabled; none of their headers or libraries enter a Foundation package. With FOUNDATION_TESTING=OFF, GoogleTest is neither downloaded nor added to the build graph.

Native and Cross Tests

Native presets may build and execute CTest programs on the host. Cross presets create binaries for a different processor and cannot be treated as host executable tests. AVR, STM32, PSoC, and generic Arm targets require one of:

  • tests compiled into the consuming firmware and executed on hardware;
  • a target-aware emulator with an explicit CMake/CTest launcher;
  • host-side tests built from the same portable source using a native preset.

Validate embedded outputs with Validation and do not report AllowNoTests as a successful test suite.
