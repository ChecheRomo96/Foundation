This page describes the workflow a developer runs manually from a local checkout. CI should invoke the same repository scripts on the appropriate native or cross-compilation runner; it should not duplicate their CMake sequence in workflow YAML.

Execution Model

Every command starts with a target preset such as macos_arm64, windows_msvc_x64, stm32f407_armgcc_cortex_m4f_hard, or atmega328p_avrgcc_avr5. The preset is the compatibility identity: it selects the platform, compiler/toolchain, architecture, ABI, and generator. Debug and Release are configurations inside that one identity, not separate presets.

The scripts use two repository-owned locations:

build/<preset>/ CMake cache, generated build system, objects, and artifacts
dist/<preset>/ Installed package intended for consumption or publication

build/ is disposable. dist/ is a package result. Do not publish files directly from the build tree.

Prerequisites

From the repository root, first confirm that CMake can see the target preset and the required compiler:

cmake --version
cmake --list-presets=all
ninja --version

Ninja is required by the current macOS, Clang, Linux, Arm, and AVR presets. Visual Studio presets instead require the matching Visual Studio installation and should be run from Developer PowerShell. Cross presets additionally need their target compiler and runtime/sysroot. Doxygen is needed only for the documentation workflow.

Daily Development

The build script configures before compiling, so a separate configure command is not required for a normal edit/build cycle.

./scripts/build.sh macos_arm64 --config Debug --target Foundation
./scripts/build.ps1 windows_msvc_x64 `
-Configuration Debug -Target Foundation

Repeating the command is incremental. Use Release explicitly when optimizing or checking the release configuration:

./scripts/build.sh macos_arm64 --config Release --target Foundation

Omitting --target Foundation or -Target Foundation builds the generator's default target and can include optional targets enabled in the current cache. Selecting Debug or Release does not require --fresh and does not create a second preset directory.

Explicit Configuration and Overrides

Run configure directly when inspecting the configure summary or selecting a custom feature set:

./scripts/configure.sh macos_arm64 --fresh -- \
-DFOUNDATION_FULL_BUILD=OFF \
-DFOUNDATION_SCHEDULING=OFF
./scripts/configure.ps1 windows_msvc_x64 -Fresh `
-CMakeArguments "-DFOUNDATION_FULL_BUILD=OFF", `
"-DFOUNDATION_SCHEDULING=OFF"

Cache overrides remain associated with build/<preset> until another configure operation replaces them or the cache is refreshed. If an override must apply to an export, pass it to the export command itself; do not rely on an earlier configure call.

Fresh Versus Incremental

--fresh in Bash and -Fresh in PowerShell ask CMake to recreate its cache and generated build-system state. They are optional controls, not part of the target name.

Situation Fresh? Reason
Rebuild after editing source or headers No Incremental compilation is faster.
Switch between Debug and Release No The multi-config tree isolates both configurations.
Export a local package during iteration Optional Explicit command options still apply.
Create a release candidate Yes Begins from preset defaults and declared overrides.
Change compiler, generator, toolchain, SDK, sysroot, CPU, FPU, or ABI Yes Cached detection may no longer be valid.
Suspect a stale or unexplained option Yes Removes hidden cache state.
Remove the complete build directory Use clean Fresh is not a full directory cleanup.

--fresh does not delete source files. It is also different from distribution cleanup: export refreshes the default dist/<preset> directory itself.

Tests and Examples

Tests and examples have different purposes:

  • tests provide pass/fail correctness evidence through CTest;
  • examples demonstrate public API usage and are not test evidence.

Run the native test workflow with:

./scripts/test.sh macos_arm64 --config Debug --fresh
./scripts/test.ps1 windows_msvc_x64 -Configuration Debug -Fresh

The default native feature set builds seven module-scoped GoogleTest executables, whose individual cases are discovered by CTest. Run the workflow once for Debug and once for Release and confirm that the output names and executes every expected case. --allow-no-tests or -AllowNoTests is only a diagnostic escape hatch for a deliberate zero-test feature configuration; it is not release evidence. Embedded binaries require target hardware, an emulator, or host-side portable tests as described in Validation.

Examples are excluded from ordinary packages. The export-only opt-in is:

./scripts/export.sh macos_arm64 --examples-on
./scripts/export.ps1 windows_msvc_x64 -ExamplesOn

Native macOS exports also contain the FoundationExamples.command launcher, and Windows exports contain FoundationExamples.cmd. A developer can double-click it, select any adjacent example, and read its exit code. The launcher then asks whether to return to the menu and run another or exit. Terminal and CI usage should invoke the real executable directly. Distribution packages contain Release examples only; build examples in Debug from the source tree when stepping through their code is useful.

./scripts/build.sh macos_arm64 --config Debug \
--target FoundationExamples --examples-on

Manual Install

Install overlays the already-built Release configuration into a prefix. It does not configure, compile, or remove stale files.

./scripts/build.sh macos_arm64 --config Release --target Foundation
./scripts/install.sh macos_arm64

This is useful for inspecting CMake installation behavior. For a distributable package, prefer export because it builds the complete Release artifact set and refreshes the repository-owned destination safely.

Release-Candidate Export

The normal one-command package excludes examples:

./scripts/export.sh macos_arm64 --fresh --parallel 8
./scripts/export.ps1 windows_msvc_x64 -Fresh -Parallel 8

To publish example executables in the same package, opt in explicitly:

./scripts/export.sh macos_arm64 --fresh --examples-on --parallel 8

Feature variants must declare their overrides in the export command:

./scripts/export.sh macos_arm64 --fresh -- \
-DFOUNDATION_FULL_BUILD=OFF \
-DFOUNDATION_SCHEDULING=OFF

Place --examples-on before the -- separator when combining it with raw CMake arguments. Export configures once, builds Release, removes the default dist/<preset>, and installs that configuration into the directory. The expected native Unix library is libFoundation.a; Windows produces Foundation.lib. Optional examples are also Release artifacts.

Installed Package Consumer

The release-package acceptance command exports Foundation, configures a standalone consumer from only that prefix, links the imported target, and runs the resulting program:

./scripts/test-package.sh macos_arm64 --fresh --parallel 8
./scripts/test-package.ps1 windows_msvc_x64 -Fresh -Parallel 8

If the package was just exported manually, use --skip-export in Bash or -SkipExport in PowerShell to validate it without rebuilding. See Package Consumer Validation for the isolation guarantees, custom-package option, and native-execution boundary.

Verification Before Publication

A successful command is necessary but not sufficient. Before publishing:

  1. confirm the Release archive exists and no Debug archive was packaged;
  2. confirm include/ and lib/cmake/Foundation/ exist;
  3. inspect FoundationBuildInfo.cmake for the platform, compiler, architecture, feature set, and example selection;
  4. inspect archive architecture with the platform tool;
  5. run the repository package-consumer workflow, which uses find_package(Foundation CONFIG) from an isolated project;
  6. record the native or embedded validation result for that preset.

On macOS, a minimal structural inspection is:

test -f dist/macos_arm64/lib/libFoundation.a
test ! -e dist/macos_arm64/lib/libFoundation_d.a
test -f dist/macos_arm64/lib/cmake/Foundation/FoundationConfig.cmake
lipo -archs dist/macos_arm64/lib/libFoundation.a

Use Validation for target-specific checks and the release evidence checklist.

Documentation Changes

Rebuild documentation whenever a script, option, preset, toolchain, package layout, or workflow changes:

./scripts/docs.sh --fresh
./scripts/docs.ps1 -Fresh

Generated HTML belongs under build/documentation/docs/html; only the Doxygen source files under docs/ are maintained as repository documentation.
