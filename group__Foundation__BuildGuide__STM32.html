STM32 Cortex-M3, M4F, and M7F target families.

STM32 support should be separated by family/core/FPU mode.

Supported target presets:

stm32g0b1cbt6_armgcc_cortex_m0plus_soft
stm32f103_armgcc_cortex_m3_soft
stm32f407_armgcc_cortex_m4f_hard
stm32h743_armgcc_cortex_m7f_hard

These presets map to reusable core/ABI profiles:

Preset CPU Float ABI FPU
stm32g0b1cbt6_armgcc_cortex_m0plus_soft Cortex-M0+ soft none
stm32f103_armgcc_cortex_m3_soft Cortex-M3 soft none
stm32f407_armgcc_cortex_m4f_hard Cortex-M4 hard fpv4-sp-d16
stm32h743_armgcc_cortex_m7f_hard Cortex-M7 hard fpv5-d16

STM32 Rule

Do not assume all STM32 targets are compatible.

Separate builds when any of these change:

  • Cortex core,
  • FPU mode,
  • compiler/toolchain,
  • ABI,
  • feature macros.

Library Scope

The STM32 presets compile Foundation as a static library. They intentionally do not select a concrete STM32 device macro, CMSIS package, HAL, startup file, interrupt vector table, memory map, linker script, or programmer. Those belong to the consuming firmware and may further narrow compatibility.

stm32g0b1cbt6_armgcc_cortex_m0plus_soft is the first exact STM32 device profile. Its acceptance fixture in tests/Stm32G0B1Consumer supplies a minimal vector table, startup, and memory map for the STM32G0B1CBT6 only. It deliberately avoids HAL, CMSIS, clocks, GPIO, and serial output. Runtime results are exposed through SWD-readable symbols, so the same firmware works on a custom board without assuming its LED or UART routing.

Build and Export

Example for STM32F407:

arm-none-eabi-g++ --version
./scripts/configure.sh stm32f407_armgcc_cortex_m4f_hard --fresh
./scripts/build.sh stm32f407_armgcc_cortex_m4f_hard \
--config Debug --target Foundation
./scripts/build.sh stm32f407_armgcc_cortex_m4f_hard \
--config Release --target Foundation
./scripts/export.sh stm32f407_armgcc_cortex_m4f_hard --fresh

If the compiler cannot find stdint.h, provide a compatible Newlib/runtime and FOUNDATION_ARM_SYSROOT. A compiler executable without target headers is not a complete cross-compilation installation.

Validation

Use arm-none-eabi-objdump -f to inspect the exported Release archive and verify the effective flags in build/<preset>/compile_commands.json. Then link the package into the real firmware using the same CPU/FPU/ABI flags. Hardware or emulator execution is the behavioral test; host CTest cannot execute Cortex-M objects. See Validation for the full checklist.

For the exact STM32G0B1CBT6 profile, build, link, and inspect the repository firmware consumer with:

./scripts/test-stm32.sh \
stm32g0b1cbt6_armgcc_cortex_m0plus_soft \
--fresh --parallel 4

PowerShell exposes the same workflow:

./scripts/test-stm32.ps1 `
stm32g0b1cbt6_armgcc_cortex_m0plus_soft `
-Fresh -Parallel 4

This command proves the package, Cortex-M0+/soft-float identity, vector and memory placement, final link, absence of undefined symbols, and the presence of out-of-line Foundation Time symbols. It does not claim target execution.

STM32G0B1 Hardware Acceptance

The firmware stops in FoundationValidationHalt() after its checks. Load the generated FoundationStm32G0B1Consumer.elf with STM32CubeIDE or an ST-LINK GDB server, set a breakpoint on that function, reset, and run. Inspect these global symbols:

Symbol Passing value
FoundationValidationState 0x50415353 (PASS)
FoundationValidationPassed 14
FoundationValidationTotal 14

A command-line GDB session connected to an already-running ST-LINK GDB server can use:

arm-none-eabi-gdb FoundationStm32G0B1Consumer.elf
(gdb) target extended-remote localhost:61234
(gdb) monitor reset halt
(gdb) load
(gdb) break FoundationValidationHalt
(gdb) continue
(gdb) x/wx &FoundationValidationState
(gdb) x/wd &FoundationValidationPassed
(gdb) x/wd &FoundationValidationTotal

The GDB-server port is environment-specific; use the value reported by STM32CubeIDE or STM32CubeProgrammer. Record the tool versions, exact MCU, flash verification, three observed values, and the commit SHA in Validation before changing VAL-008 to DONE.
