Detailed Description

Repeatable configure, build, test, install, export, and maintenance workflows.

Foundation uses CMake presets to describe a target and small repository scripts to execute a workflow. The scripts do not contain platform-specific compiler logic. A preset selects the platform, architecture, compiler, generator, and cross-compilation toolchain. Debug or Release is selected by the workflow and is deliberately not part of the preset identity.

Bash scripts are provided for macOS, Linux, and compatible shells. Matching PowerShell scripts provide the same operations on Windows. Every script resolves the repository root from its own location, so it can be invoked from any working directory.

Responsibilities

The build system is split into four layers:

  • CMakePresets.json and cmake/presets/ define supported artifact identities and reproducible target defaults;
  • cmake/toolchains/ defines cross-compilers, CPU flags, ABI flags, target runtimes, and program lookup rules;
  • CMake cache options select Foundation modules or machine-local SDK paths;
  • scripts/ performs one operation consistently without duplicating target knowledge.

A workflow script is an interface to CMake, not a second build system. When a target changes, update its preset or toolchain. When the sequence of CMake operations changes, update the script.

Workflow Directories

build/<preset>/ Temporary CMake cache and build artifacts
dist/<preset>/ Installed package; redistribution requires authorization
docs/Workflows/ Source documentation for these workflows

Build directories are disposable. Distribution directories are created only by install or export operations and must remain separated by target preset. Official packages contain only the Release library. Compiler, architecture, ABI, and feature-set changes require a different package or a deliberate custom re-export. Debug remains available inside the source build tree.

Cached State

configure, build, test, and export reuse build/<preset> unless their fresh option is supplied. This is convenient during development, but cache overrides not explicitly replaced by the preset or script can remain active. The test workflow enables testing only; examples remain independent. Use a fresh export for release candidates so the package starts from preset defaults plus only the overrides shown in the release command.

Normal Release Sequence

./scripts/configure.sh macos_arm64 --fresh
./scripts/build.sh macos_arm64 --config Debug --parallel 8
./scripts/test.sh macos_arm64 --config Debug --parallel 8
./scripts/test.sh macos_arm64 --config Release --parallel 8
./scripts/test-package.sh macos_arm64 --fresh --parallel 8

The test steps must report and execute the registered suite; a zero-test result is a release-gate failure. The package-consumer step performs the Release export and proves that a standalone project can link it. See Test and Package Consumer Validation.

The Windows equivalent uses the matching .ps1 scripts. Cross-compiled targets do not run host-side CTest executables; follow Validation for their compile, export, architecture, and firmware-consumer checks.
