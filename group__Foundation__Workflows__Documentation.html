Generate the Doxygen HTML site through the normal build workflow.

Documentation is configured by the documentation preset and built as the CMake docs target. It is intentionally kept inside the same preset/script architecture as the library so local development and CI use one command.

Bash

./scripts/docs.sh [preset] [build options]
./scripts/docs.sh
./scripts/docs.sh documentation --fresh --parallel 8

PowerShell

./scripts/docs.ps1 [-Preset <preset>] [-Parallel <jobs>] [-Fresh]

The default preset is documentation. It enables FOUNDATION_DOCS, requires a discoverable Doxygen installation, and builds the docs target. Generated HTML is written to:

build/<preset>/docs/html/index.html

Documentation sources must be registered with foundation_add_dox() from a CMakeLists file. Workflow pages are registered by docs/Workflows/CMakeLists.txt. Platform pages are registered by docs/Topics/BuildGuide/CMakeLists.txt.

Define a page with @defgroup, attach it to exactly one subgroup with @ingroup, add a concise @brief, use globally unique section identifiers, and register the file in the local CMakeLists. Platform-specific integration belongs under Build Guide / Platforms; reusable command behavior belongs here.

Collapsible Indexes

The generated Topics and Class List pages open at detail level 2: modules and namespaces remain visible while their child entries start collapsed. Readers can use the native Doxygen arrows or detail level controls to expand the hierarchy.

Doxygen does not expose a configuration value for the initial detail level. docs/assets/FoundationDocs.js applies the default by calling Doxygen's own dynsection.toggleLevel() implementation, and FoundationFooter.html loads that script through HTML_FOOTER and HTML_EXTRA_FILES. If the project upgrades Doxygen, compare the custom footer against the new generated default before accepting the upgrade.

Quality Checks

After changing documentation:

./scripts/docs.sh --fresh

Confirm that the command succeeds, the expected group HTML exists, new pages appear below the intended parent, and the output contains no unresolved references, malformed commands, or duplicate section labels. The checked-in configuration intentionally disables WARN_IF_UNDOCUMENTED: API coverage is incomplete and is tracked as a separate release task, while structural and semantic documentation errors remain visible. Do not suppress a new warning merely because older public APIs still need descriptions.
