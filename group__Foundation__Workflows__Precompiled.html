Compatibility and consumption rules for exported static libraries.

Precompiled libraries reduce build time for projects that consume Foundation, while the repository remains the source of truth. An exported library is only compatible with the operating system, compiler/toolchain, architecture, ABI, build configuration, and compiled feature macros used to create it.

A Windows MSVC .lib is not assumed to be compatible with MinGW. An Arm GNU Cortex-M3 soft-float .a is not compatible with a Cortex-M4 hard-float target. Keep each target package in its own dist/<preset> directory. Official packages contain Release objects only.

Compatibility Matrix

Rebuild or select another package whenever one of these changes:

Dimension Examples Why it matters
operating system/object format Windows COFF, macOS Mach-O, ELF Linkers consume different formats.
compiler/toolchain MSVC, Apple Clang, Arm GNU, AVR-GCC Name mangling, runtime, and flags may differ.
architecture/core x86-64, arm64, Cortex-M3, AVR5 Machine instructions are target-specific.
ABI/FPU Arm soft float, M4F hard float Function calling conventions differ.
C++ runtime policy exceptions/RTTI enabled or disabled Runtime symbols and object assumptions differ.
feature options Scheduling on/off Headers, macros, and compiled symbols differ.
configuration Release Official packages contain optimized Release objects only.

Debug is a source-build configuration used for development and tests; it is not a distributed precompiled package. Every other incompatible dimension belongs in the preset identity or in a deliberately isolated custom feature package.

Full Build

A full build enables all Foundation modules. It is useful for desktop integration, testing, examples, and quick prototyping.

Custom Build

A custom build enables only the modules required by a product. It is useful for embedded systems, memory-sensitive projects, and production firmware. Configure feature options before exporting and preserve the preset identity with the resulting package.

The feature set is part of package compatibility even though it is not part of the normal preset name. Store custom variants in separate distribution paths, retain their FoundationBuildInfo.cmake, and never overlay two variants.

Recommended Flow

./scripts/configure.sh <preset> --fresh
./scripts/test.sh <preset> --config Debug
./scripts/export.sh <preset>

On Windows:

./scripts/configure.ps1 <preset> -Fresh
./scripts/test.ps1 <preset> -Configuration Debug
./scripts/export.ps1 <preset>

The native GoogleTest suite is the release gate described in Test. For cross-compiled targets, replace host CTest execution with firmware/consumer validation described in Validation.

Consumer Contract

A CMake consumer should use:

find_package(Foundation 1.0 CONFIG REQUIRED)
target_link_libraries(MyTarget PRIVATE Foundation::Foundation)

The imported target carries include directories, compile features, public definitions, and the Release archive mapping. Consumers must not copy only the archive and omit the installed headers/package metadata. Debug consumers must build Foundation from source.

See Export for package contents and find_package(Foundation CONFIG) integration.
