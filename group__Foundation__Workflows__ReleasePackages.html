Build validated archives and publish immutable GitHub Release assets.

.github/workflows/release.yml converts an existing version tag into the downloadable precompiled packages consumed through find_package. This is separate from the Continuous Integration workflow. Native CI proves every main-branch change, while the release workflow rebuilds and publishes the exact tagged source.

Triggers and Publication

Pushing a tag beginning with v starts the workflow and publishes the resulting GitHub Release automatically. The tag must match the version in CMakeLists.txt. Stable and release-candidate examples are:

v1.2.0
v1.3.0-rc.1

workflow_dispatch requires an existing tag. By default it only creates temporary workflow artifacts for inspection. Selecting its publish input additionally creates the GitHub Release. This makes manual packaging safe to rehearse without publishing a release accidentally.

Every matrix job performs a fresh Release export and executes the standalone package consumer before creating its archive. A final verification job downloads the complete set, requires exactly five archives and five checksum files, and verifies every SHA-256 digest even when publication is disabled. Packages do not include Debug libraries or examples. Every package includes LICENSE, README.md, and CHANGELOG.md. Each archive contains one top-level directory named Foundation-<release>-<preset> and is accompanied by a .sha256 file.

A release-candidate asset uses the tag suffix in its filename even though the CMake package reports the numeric project version. For example, v1.3.0-rc.1 produces Foundation-1.3.0-rc.1-macos_arm64.tar.gz.

Consuming a Download

Extract the archive, then add its top-level directory to CMake's prefix search path:

cmake -S . -B build \
-DCMAKE_PREFIX_PATH=/path/to/Foundation-1.2.0-macos_arm64

The consuming project uses only the exported CMake target:

find_package(Foundation 1.0 CONFIG REQUIRED)
target_link_libraries(MyApplication PRIVATE Foundation::Foundation)

Foundation_DIR may instead point directly to <prefix>/lib/cmake/Foundation. Consumers must select the package matching their operating system, architecture, compiler ABI, and Release policy. GitHub Actions artifacts are short-lived validation output; GitHub Release assets are the supported downloadable distribution channel.

Release Procedure

Before creating a publishing tag:

  1. complete the applicable gates in Foundation 1.x Stabilization Backlog;
  2. ensure native CI is green on the exact commit;
  3. create and push an annotated tag;
  4. wait for all package jobs and checksum verification to succeed;
  5. inspect the published release and test a clean external download.
git tag -a v1.3.0-rc.1 -m "Foundation v1.3.0-rc.1"
git push origin v1.3.0-rc.1

A failed package job prevents publication. A tag is a release decision, not merely a request to test an arbitrary branch, and should not be moved after packages have been published.
