Foundation has now exercised the same configure, build, test, install, export, package, and CI concepts across desktop, AVR, generic Arm, Arduino, and an exact STM32 firmware consumer. That is enough evidence to identify a reusable layer. It is not yet permission to move every build-related file. Project policy and acceptance tests must remain with the project that owns them.

The selected direction is a small, separately versioned build-infrastructure repository named RoModularBuild. Foundation and future projects such as MCC will pin an exact infrastructure revision and retain thin repository-local adapters. An optional romodular command-line frontend may be added later; the initial extraction must continue to work through the existing .sh and .ps1 entrypoints.

Goals and Non-goals

Goals:

  • define native and cross-compilation profiles once;
  • keep Bash and PowerShell workflow behavior equivalent;
  • give every repository reproducible, version-pinned infrastructure;
  • preserve build/<preset> and dist/<preset> conventions;
  • keep presets as the source of truth for compiler, architecture, and ABI;
  • keep Debug and Release as configurations, not separate preset identities;
  • allow project-specific feature options and package targets without teaching the shared layer about Foundation or MCC; and
  • make upgrades explicit, reviewable, and independently reversible.

Non-goals:

  • turning CMake into a hidden secondary build system;
  • putting Foundation modules, tests, package metadata, or release policy in a shared repository;
  • defining startup code, linker scripts, HAL/CMSIS, flashing, or board wiring for every microcontroller;
  • generating one precompiled Foundation package per Arm part number;
  • requiring Docker for native Windows or macOS validation; or
  • creating the final romodular CLI before the underlying contract is stable.

Target Architecture

The shared repository must not depend on Foundation, MCC, or any other consumer. Dependency direction is one-way: a project selects a pinned infrastructure version and adds its own adapter and acceptance policy.

Workflow Adapter Contract

Foundation preserves the same public Bash and PowerShell commands. The five lifecycle entrypoints are intentionally thin:

scripts/configure.* -> tools/RoModularBuild/scripts/configure.*
scripts/build.* -> tools/RoModularBuild/scripts/build.*
scripts/test.* -> tools/RoModularBuild/scripts/test.*
scripts/install.* -> tools/RoModularBuild/scripts/install.*
scripts/clean.* -> tools/RoModularBuild/scripts/clean.*

scripts/romodular-adapter.sh and scripts/romodular-adapter.ps1 provide only repository-owned values:

Adapter value Foundation value Purpose
project root repository root Locates CMakePresets.json and relative caller paths.
build root build/ Preserves build/<preset> identities.
distribution root dist/ Preserves default install/export destinations.
default configuration Debug Preserves interactive build and test behavior.
documentation configuration preset documentation uses Release Preserves the Doxygen build contract.
install configuration Release Prevents accidental Debug package installation.
testing cache argument -DFOUNDATION_TESTING=ON Keeps the generic engine independent of Foundation option names.
examples cache argument -DFOUNDATION_EXAMPLES=ON Maps the existing examples switch without moving example policy.

The shared scripts own argument validation, safe build-directory selection, CMake/CTest invocation, full fresh-state deletion, configuration selection, JUnit forwarding, no-tests-as-error, install defaults, and scoped cleaning. Foundation's common.* files retain compatibility aliases because package, example, Arduino, STM32, documentation, and release scripts still consume the established foundation_* helpers. This avoids a flag day and keeps those policy-heavy workflows local.

A missing submodule fails before CMake with the exact initialization command. The shared files contain no FOUNDATION_* or MCC_* implementation names; project-specific cache arguments exist only in the Foundation adapter.

Preset and Toolchain Contract

The shared layer provides hidden or clearly prefixed base presets. A project publishes its own preset by inheriting a shared base and adding local cache values. For example, the shared layer may define a Cortex-M0+/soft-float base, while Foundation continues to publish arm_none_eabi_cortex_m0plus_soft and records FOUNDATION_PLATFORM locally.

Shared cache variables use the ROMODULAR_ prefix. Project feature options retain their project prefix. The migration must temporarily accept the existing Foundation toolchain variables so saved commands do not break; the shared names become canonical only after both paths produce identical flags.

Package boundaries remain based on binary compatibility:

  • native packages: operating system, compiler/toolchain, and architecture;
  • generic Arm packages: instruction-set core, float ABI, FPU, compiler/runtime, and relevant flags;
  • AVR packages: the exact MCU may remain necessary because -mmcu controls device-specific code generation and runtime selection; and
  • firmware targets: exact MCU/board memory map, startup, device SDK, and programming procedure.

Therefore, STM32G0B1CBT6 is an exact Foundation acceptance target, while the reusable library compatibility profile is Cortex-M0+/soft-float. The shared repository must not grow one generic Arm library preset per MCU.

Distribution and Pinning

The first integration uses a Git submodule at a stable relative path such as tools/RoModularBuild. Each project pins an exact commit belonging to a tagged infrastructure release. This solves the bootstrap constraint: CMake parses presets and loads a toolchain before the project can use FetchContent, so the required files must already exist before configure.

Required operational rules:

  • clone with submodules or run the documented initialization command;
  • CI checkout enables submodules explicitly;
  • upgrades change one recorded submodule commit and run the complete project matrix before merge;
  • no branch-floating reference such as main is accepted by a consumer;
  • RoModularBuild follows an independent semantic version;
  • 0.x releases may evolve the adapter contract; 1.x freezes it; and
  • public visibility provides reproducible read access but grants no permission to use, modify, or redistribute the code; the restrictive license remains in force until separate legal review authorizes another model.

A future romodular CLI may install or update the pinned infrastructure and expose commands such as romodular build <preset>. It must remain a frontend over the same CMake presets and workflow contract, not become another source of compiler or target truth.

Reusable CI Contract

Phase 4 uses composite actions stored inside the pinned submodule rather than a remote reusable workflow with a second @ref. After recursive checkout, a consumer calls the action through its local path:

- uses: ./tools/RoModularBuild/actions/project-workflow
with:
command: test
preset: macos_arm64
configuration: Debug
fresh: true
parallel: 4

The gitlink is therefore the only RoModularBuild version pin. The local caller cannot execute action code from a different branch or tag by accident. Third-party GitHub actions retain separate dependency pins because they are independent dependencies.

The shared CI surface has two project-independent actions:

  • project-workflow selects Bash or PowerShell and invokes the consumer's configure, build, test, install, or clean adapter without accepting an arbitrary shell command; and
  • report-toolchain reports CMake, Ninja, the selected compiler, and the hosted operating system.

Foundation still owns triggers, runner and compiler matrices, permissions, concurrency, dependency installation, Foundation package and example validation, coverage policy, firmware evidence, artifact retention, documentation deployment, and release publication. The phase 4 extraction removes platform-specific invocation duplication without moving repository policy into the shared dependency.

Each phase is a separate reviewable commit or pull request. Foundation must stay buildable at every boundary. Do not delete the local implementation until the replacement has passed the same native and embedded matrices.

INFRA-001 Acceptance

INFRA-001 is complete only when:

  • the shared repository exists and has an independently tagged version;
  • Foundation pins that exact version without floating branches;
  • generic files contain no Foundation, MCC, or project-specific target names;
  • Foundation's current commands and output directories remain compatible;
  • Bash and PowerShell paths pass the hosted native matrix;
  • all advertised embedded packages retain their validated architecture/ABI;
  • package, example, Arduino, STM32, release, and legal policy remain local;
  • a second repository consumes the same release successfully; and
  • rollback consists only of restoring the previous pinned revision.

Until those gates pass, the checked-in Foundation implementation remains the authoritative and supported workflow.
