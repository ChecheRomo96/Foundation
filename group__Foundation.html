Detailed Description

Core documentation topic for the Foundation framework.

Foundation is a modular C++ framework designed for embedded and desktop software development.

The framework provides reusable software components organized into independent modules. Each module focuses on a specific domain such as mathematics, time handling, containers, scheduling, or compile-time utilities.

Overview

Foundation is intended to provide a stable base layer for projects that need reusable, lightweight, and portable C++ components.

The main design goal is to support both resource-constrained embedded systems and desktop environments without forcing unnecessary dependencies on the user.

Foundation can be used as:

  • A standalone utility library.
  • A dependency for higher-level frameworks.
  • A base layer for embedded applications.
  • A shared foundation for multiple projects.

Design Goals

Foundation is designed around the following principles:

  • Embedded-first design.
  • Desktop compatibility.
  • Modular architecture.
  • Stable public interfaces.
  • Minimal runtime overhead.
  • Minimal dependency on the C++ standard library.
  • Optional module selection through the build system.
  • Clear separation between public API and internal structure.

Type Traits Module

The Type Traits module provides compile-time type utilities.

This module is intended to provide lightweight template metaprogramming support, especially for embedded environments where depending on the full C++ standard library may not be desirable.

Math Module

The Math module provides mathematical utilities and data structures.

Typical components include:

  • Arithmetic helpers.
  • Ratios.
  • Complex numbers.
  • Fixed-size matrices.
  • Dynamic matrices.
  • Matrix operations.

Time Module

The Time module provides abstractions for representing and working with time-related values.

Typical components include:

  • Frequency.
  • Period.
  • Duration.
  • Width-explicit Tick specializations.
  • TimePoint.
  • Clock.

Containers Module

The Containers module provides reusable data structures.

This module is intended for arrays, buffers, queues, lists, or other storage abstractions that are useful across embedded and desktop projects.

Functional Module

The Functional module provides callable and callback utilities.

This module is intended for lightweight callback binding, function abstraction, delegates, and related utilities.

Scheduling Module

The Scheduling module provides utilities for managing task execution.

This module is intended for periodic tasks, one-shot tasks, deferred execution, and simple embedded-friendly scheduling systems.

Utils Module

The Utils module contains general-purpose utilities that do not yet belong to a more specific module.

This module should remain small. If a utility grows into a clear domain, it should eventually be moved into its own module.

Public API

The public API of Foundation is exposed through top-level headers.

For user-facing includes, see:

  • Top-Level Headers

Application code should prefer the top-level public headers instead of including deeply nested internal headers directly.

Build System

Foundation uses CMake as its main build system.

The build system is responsible for:

  • Enabling or disabling modules.
  • Selecting the target platform.
  • Exporting public headers.
  • Generating static libraries.
  • Generating documentation.
  • Preparing embedded distributions.

Target Platforms

All target platforms require a compiler with C++17 language support. The library avoids requiring the complete C++ standard library so that C++17 language mode remains usable on constrained embedded toolchains.

Foundation is intended to support:

  • Desktop platforms.
  • Arduino-style environments.
  • PSoC Creator projects.
  • STM32 projects.
  • Other C++17-capable embedded targets.

Coding Style

Foundation follows these general conventions:

  • PascalCase for class names.
  • PascalCase for public function names.
  • Descriptive accessor nouns such as Numerator(), Ticks(), RowCount(), Size(), and Data(); avoid unclear abbreviations.
  • Get...() for associated or configured objects when the direct noun would collide with a public type name, as in GetFrequency() and GetClock().
  • Is...() and Has...() for Boolean state queries.
  • Standard-compatible snake_case only in TypeTraits, where matching <type_traits> is part of the public contract.
  • Nested namespaces.
  • Explicit module ownership.
  • Small focused headers.
  • Minimal hidden dependencies.
  • Embedded-friendly implementations.
  • Keep short parameter lists on the same line as the function name.
  • Put a function's opening brace on the same line as its signature: ReturnType Function(parameters) {.
  • Apply the same formatting to C++ snippets in Doxygen documentation.

Top-Level Headers

Foundation exposes a set of top-level headers intended to be used directly by application code.These headers are especially important for Arduino, PSoC Creator, and other embedded environments where users usually include headers directly instead of relying on CMake targets.

Overview

The top-level headers define the public include surface of Foundation.

They provide a stable access layer that keeps application code independent from the internal folder structure of the framework.

For broad access, user code should prefer:

#include <Foundation.h>
#include <Foundation_Math.h>
#include <Foundation_Time.h>

A documented component header is also a supported public entry point when code needs a narrow dependency:

#include <Foundation/Math/Ratio.h>
#include <Foundation/Time/Clock.h>

Headers ending in .tpp are installed only because the declaring template headers include their definitions. They are implementation dependencies, not direct consumer entry points. Include the matching .h instead; it brings in the required .tpp automatically. Other internal headers may exist inside the Foundation source tree but are not part of the supported consumer interface.

Main Header

Foundation.h

The Foundation.h header is the main public entry point of the framework.

It includes the public interface of the enabled Foundation modules.

Use this header when the application needs broad access to the enabled Foundation functionality.

Example:

#include <Foundation.h>
void setup() {
}
void loop() {
}

This include style is convenient for:

  • Arduino sketches.
  • Examples.
  • Prototypes.
  • Small embedded applications.
  • Applications that use several Foundation modules.

Build Settings Header

Foundation_BuildSettings.h

The Foundation_BuildSettings.h header exposes build configuration macros.

These macros describe the Foundation version, active C++ language level, and which modules or features are available in the current build. FOUNDATION_VERSION reports 1.2.0. FOUNDATION_CPLUSPLUS follows _MSVC_LANG on MSVC and __cplusplus elsewhere. Including the header from a language mode older than C++17 produces a compile error.

The header does not invent platform markers or include target SDK headers. Platform detection remains the responsibility of the compiler, toolchain, and consuming application until Foundation exposes a concrete portable abstraction that requires it.

Example:

#include <Foundation_BuildSettings.h>
#ifdef FOUNDATION_MATH
// Math module is available.
#endif

This header is useful when writing code that must adapt to different Foundation distributions.

Include Strategies

Foundation supports two main include strategies:

  • Full include.
  • Selective include.

Full Include

Use the main Foundation.h header when the application needs access to several modules or when simplicity is preferred.

Example:

#include <Foundation.h>

This style is recommended for:

  • Arduino sketches.
  • PSoC Creator applications.
  • Examples.
  • Quick tests.
  • Small applications.

Selective Include

Use individual module headers when the application only needs specific parts of the framework.

Example:

#include <Foundation_Math.h>
#include <Foundation_Time.h>

This style is recommended for:

  • Library code.
  • Public headers.
  • Larger projects.
  • Embedded applications with strict dependency control.
  • Projects where compile-time dependencies should remain explicit.

Arduino Usage

Arduino users should normally include Foundation through top-level headers.

Basic example:

#include <Foundation.h>
void setup() {
}
void loop() {
}

Selective include example:

#include <Foundation_Math.h>
#include <Foundation_Time.h>
void setup() {
}
void loop() {
}

Top-level headers avoid exposing Arduino sketches to the internal source tree layout of Foundation.

PSoC Creator Usage

In PSoC Creator projects, Foundation is usually consumed through an exported distribution containing:

  • Public headers.
  • Precompiled static libraries.
  • Build settings.

Application code should include top-level headers from the exported include directory.

Example:

#include <Foundation.h>

or:

#include <Foundation_Math.h>

Desktop Usage

Desktop projects may use the same top-level headers as embedded projects.

When using CMake, the recommended workflow is:

  • Add or find the Foundation package.
  • Link the Foundation target.
  • Include the required top-level headers.

Example:

#include <Foundation.h>

Public API Policy

The top-level headers define the intended public include interface of Foundation.

Application code should treat these headers as the stable entry points of the framework.

Headers located deeper inside the Foundation source tree may be reorganized as the framework evolves.

Recommended:

#include <Foundation_Math.h>

Avoid in application code:

#include <Foundation/Math/Matrix/Fixed.h>
Fixed.h
Fixed-size matrix type.

Internal headers may still be documented, but they should not necessarily be considered the preferred user-facing include path.

Header Responsibility

Top-level headers should:

  • Expose the public module interface.
  • Include only public module headers.
  • Avoid exposing private implementation details.
  • Remain stable across internal folder reorganizations.
  • Match the enabled build configuration.

Top-level headers should not:

  • Contain large implementations unless required by templates.
  • Include unrelated modules unnecessarily.
  • Become a replacement for clear module boundaries.
  • Expose experimental internals as public API.

Module Availability

The exact contents of each top-level header may depend on the enabled modules in the current build.

Reduced embedded builds may expose fewer modules than full desktop builds.

Code that depends on optional modules should check the corresponding build macros when necessary.

Example:

#include <Foundation_BuildSettings.h>
#ifdef FOUNDATION_TIME
#include <Foundation_Time.h>
#endif

Recommended Usage

For most applications:

#include <Foundation.h>

For module-specific application code:

#include <Foundation_Math.h>

For library headers:

#include <Foundation_Math.h>
#include <Foundation_Time.h>

For conditional builds:

#include <Foundation_BuildSettings.h>
#ifdef FOUNDATION_MATH
#include <Foundation_Math.h>
#endif
