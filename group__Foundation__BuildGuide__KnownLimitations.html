This page records limitations that affect Foundation 1.x consumers and future release decisions. It complements the Support Matrix: the matrix classifies targets, while this page explains boundaries that apply across targets and workflows.

A limitation remains listed until evidence removes it. A preset, successful configure, or compiled archive is not sufficient evidence by itself.

Release and License Status

  • Foundation 1.2.0 is the current published release. Version 1.1.0 was the first published release; the planned 1.0.0 tag was superseded.
  • Foundation is currently proprietary and grants no permission for external use, compilation, modification, integration, or redistribution without a separate written authorization.
  • The final license, ownership, contribution, and distribution model require review by qualified legal counsel. This blocks any external-use grant; it is not a documentation disclaimer that can be waived by a build option.
  • The source repository, examples, generated documentation, and exported artifacts all remain subject to the current LICENSE notice.
  • The preparation checklist and unresolved ownership/licensing questions are tracked in License and Ownership Review. That record is not legal advice and does not replace review by qualified counsel.

Platform Scope

Rows marked RELEASE CANDIDATE or PUBLISHED in the support matrix are not SUPPORTED until their full acceptance evidence passes. PSoC 5LP and generic Arm profiles are experimental. PIC is explicitly deferred and has no current preset, package, or compatibility promise.

Cross-compiled archives do not provide a complete firmware environment. Foundation does not supply a target C runtime, startup code, interrupt vectors, CMSIS, vendor HAL, device definitions, memory layout, linker script, flashing workflow, or board support package. The consuming firmware owns those components and must match the archive's compiler, CPU, ABI, FPU, and runtime assumptions.

Package Boundaries

  • Exported packages contain one target-specific Release static library. Debug libraries remain source-build artifacts and are not distributed.
  • There is no universal/fat package, runtime architecture dispatch, shared library, system installer, or package-manager publication in version 1.x.
  • Packages with different compilers, standard-library ABIs, CPU flags, or feature selections are not interchangeable and must not be merged.
  • The repository package-consumer fixture currently validates the default feature set, including Math and Time. The complete feature-option package matrix remains tracked as PKG-002.
  • Direct source inclusion is available for Arduino-style and internal use, but the exported CMake package is the primary Foundation 1.x desktop consumer contract.

Runtime and API Boundaries

  • Every integration mode requires a C++17-capable compiler. Foundation avoids requiring the complete C++ standard library, but C++14 and older are not supported.
  • TypeTraits intentionally implements the subset used and documented by Foundation; it is not a complete replacement for <type_traits>.
  • Containers and TaskScheduler use caller-owned, fixed-capacity storage. They do not allocate, resize, own, or destroy the supplied arrays.
  • Callback is allocation-free and does not own bound objects. Bound objects, contexts, clocks, tasks, and external storage must outlive their users.
  • TimePoint ordering and Duration arithmetic use modular half-range rules. Intervals at or beyond the selected tick type's half-range are ambiguous or invalid by contract.
  • Heap-backed dynamic matrices depend on the target runtime's allocation backend. Allocation failure is reported without exceptions; attached caller-owned storage is the deterministic alternative.

Consult the relevant module documentation for the exact ownership, invalid state, aliasing, rollover, and exception contracts.

Quality Gates Still Open

The current suite is meaningful but is not the final quality ceiling. The inventoried Math and remaining-module behavior gaps are closed. Standalone compilation of every public header, agreed compiler-warning policies, sanitizers, and a coverage baseline with an explicit threshold remain open release tasks. Examples demonstrate API use and are never counted as tests.

The maintained release scope is summarized in the repository CHANGELOG.md. Update this page, the changelog, support matrix, and release backlog together whenever evidence changes one of these statements.
