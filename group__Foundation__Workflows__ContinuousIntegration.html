Native, documentation, and embedded GitHub Actions validation.

.github/workflows/native-ci.yml executes Foundation's repository scripts on native GitHub-hosted runners. The workflow YAML selects a runner and preset; it does not reproduce the configure, build, test, export, or consumer logic already owned by scripts/.

Generic cross-platform lifecycle invocation and toolchain reporting use the composite actions in the exact RoModularBuild revision checked out at tools/RoModularBuild. The local action path is governed by the same gitlink as the shared scripts and toolchains, so CI does not introduce a second RoModularBuild version reference. Foundation keeps its triggers, matrices, permissions, package and example gates, artifacts, and release policy in this repository. See Reusable CI Contract.

Triggers and Permissions

Native CI runs for:

  • pull requests targeting main;
  • pushes to main;
  • explicit workflow_dispatch requests.

It has read-only repository permission and uses no project secrets. A concurrency group cancels an older run for the same branch or pull request when a newer commit supersedes it. Matrix fail-fast is disabled so one compiler failure does not hide the state of the other platforms.

Job Sequence

Every matrix entry performs the same acceptance sequence:

  1. report CMake, Ninja, compiler, OS, and architecture information;
  2. configure fresh, build, and run the registered suite in Debug;
  3. build and run the same suite in Release from the multi-config tree;
  4. perform a fresh Release export and verify its exact contents, metadata, compiler/ABI identity, and real archive architecture;
  5. recreate the standalone package consumer, find only that exported prefix, link Foundation::Foundation, and execute the consumer test;
  6. prove the identity gate rejects an added Debug archive, a missing public header, and modified build-identity metadata;
  7. discover every desktop example definition, build and execute its Debug and Release forms, require identical output, export only Release executables, execute the exported copies, and exercise the native launcher where one exists.

Debug and Release do not name separate test suites. The same tests execute against both library configurations. Debug remains a development artifact; the exported and consumer-tested package contains Release only.

Bash runners invoke:

./scripts/test.sh <preset> --config Debug --fresh --parallel 4
./scripts/test.sh <preset> --config Release --parallel 4
./scripts/test-package.sh <preset> --fresh --parallel 4
./scripts/validate-examples.sh <preset> --fresh --parallel 4

Windows runners invoke the equivalent .ps1 commands. Both test scripts reject an empty CTest suite, and test-package forces a real archive link by calling out-of-line Time symbols. See Test and Package Consumer Validation.

Example validation remains separate from CTest because examples demonstrate API use; they are not correctness tests. validate-examples.sh and validate-examples.ps1 discover the example definitions and artifacts instead of maintaining a hardcoded executable list. Linux validates direct execution and intentionally expects no launcher. macOS and Windows also run scripted quit and single-example launcher scenarios; opening the launcher through Finder or Explorer remains a manual user-experience check.

The native Arm64 runner is equivalent CPU/OS evidence for the Linux Arm64 package identity. It is useful preparation for a Raspberry Pi consumer, but it does not prove Raspberry Pi board, kernel, peripheral, or deployment behavior.

Embedded Matrix

.github/workflows/embedded-ci.yml cross-compiles every public AVR and Arm preset on ubuntu-24.04. It installs the matching GNU toolchain, builds the Foundation target in Debug and Release, performs a fresh Release export, inspects every archive with target binutils, rejects Debug files in the package, verifies the Release import mapping and build metadata, and uploads the validated package for inspection.

The matrix contains ATmega328P/AVR5; the four generic Cortex-M profiles; PSoC 5LP; and the STM32G0B1CBT6, STM32F103, STM32F407, and STM32H743 identities. The exact STM32G0B1 job additionally links and inspects the repository-owned firmware consumer and uploads its ELF, HEX, BIN, and map. These jobs deliberately do not invoke target CTest, execute target code on the x86-64 runner, or claim hardware proof.

Warnings and Sanitizers

When FOUNDATION_TESTING is on, foundation_enable_warnings compiles the Foundation library, every test executable, and the header self-containment target with warnings as errors: /W4 /permissive- on MSVC and -Wall -Wextra -Wpedantic -Wshadow -Wconversion -Wsign-conversion -Wold-style-cast -Wnon-virtual-dtor -Woverloaded-virtual elsewhere. Every native job therefore enforces the warning set. Consumer and embedded builds, which do not enable testing, keep their own flags. Locally, pass --compile-no-warning-as-error to CMake to downgrade the errors.

The sanitizers job in native-ci.yml runs the Debug suite with AddressSanitizer and UndefinedBehaviorSanitizer (-fno-sanitize-recover=all) on Linux GCC and Clang x64 and on macOS Apple Clang Arm64. MSVC offers no UndefinedBehaviorSanitizer and is not part of this job.

Coverage

The coverage job in native-ci.yml builds the Debug suite with GCC on Ubuntu x64 and FOUNDATION_COVERAGE=ON, then runs gcovr 8.6 over src/ and the staged include tree (header-only code is compiled from the staged copies). Tests and GoogleTest are excluded. The job writes a line/function/branch summary to the workflow page, uploads a browsable HTML report as the coverage-report artifact, and fails when line coverage drops below 90%, the agreed 1.x threshold.

To produce the same report locally with Apple Clang:

cmake --preset macos_arm64 -DFOUNDATION_TESTING=ON -DFOUNDATION_COVERAGE=ON --fresh
cmake --build build/macos_arm64 --config Debug
ctest --test-dir build/macos_arm64 -C Debug
mkdir -p coverage
gcovr --gcov-executable "xcrun llvm-cov gcov" -r . build/macos_arm64 \
--filter build/macos_arm64/include/ --filter src/ --html-details coverage/index.html

Baselines after TEST-004/TEST-005: GCC in CI measured 93.0% lines (1347/1448), 98.9% functions, and 72.2% branches in GitHub Actions run 36227132453; Apple Clang locally measured 88.8% lines (1184/1334), 99.0% functions, and 65.4% branches. The compilers count template and inline lines differently.

Boundaries

This native matrix does not claim the following evidence:

  • macos_x64, which requires an Intel runner or Rosetta execution and is validated locally through Rosetta 2 (VAL-002);
  • Raspberry Pi-specific integration and hardware behavior;
  • STM32 or PSoC hardware behavior, and Arduino board execution (sketches are compiled, not run); STM32G0B1 firmware linkage is checked separately from its pending hardware execution;
  • branch-coverage gates; only line coverage is enforced.

Those concerns retain separate backlog tasks. In particular, embedded jobs must never report cross-compilation as target execution.

Documentation Validation

.github/workflows/deploy-docs.yml validates Doxygen 1.14.0 on pull requests targeting main, pushes to main or master, and manual dispatches. The validation job has read-only repository permission, performs a fresh build, and uploads the generated HTML as a short-lived workflow artifact. A separate deployment job runs only for push events, consumes that validated artifact, and alone receives permission to update the docs branch. Doxygen uses WARN_AS_ERROR = FAIL_ON_WARNINGS, so structural and reference warnings fail validation before deployment.

Failure Evidence

Native Debug, Release, sanitizer, coverage, and package-consumer tests write JUnit XML through the repository scripts. If a job fails, GitHub Actions retains the available JUnit files, CTest Testing/Temporary logs, CMake cache/configure logs, and any partially exported package for 14 days. Feature-matrix failures retain the failing case's build tree. Embedded jobs retain CMake diagnostics and any package prefixes produced before an identity failure. Documentation failures retain the complete captured build log and generated Doxyfile. Release packaging and complete-set verification use the same failure-only retention policy.

Failure artifacts are diagnostic evidence, not distributable packages. They are uploaded only when the owning job fails and may be incomplete by design; successful validated packages keep their existing shorter-lived artifact names and policies.

.github/workflows/failure-evidence.yml is a manual-only acceptance probe for this policy. It is never triggered by a push or pull request. When dispatched with confirm_controlled_failure=true, one Ubuntu/Bash job and one Windows/PowerShell job create representative CMake, CTest, JUnit, and partial-package diagnostics, then intentionally exit with code 23. Their if: failure() steps upload separate 14-day artifacts. A final Ubuntu job downloads both artifacts and verifies every expected file and marker. The probe jobs use job-level continue-on-error, so an expected failure does not make the acceptance workflow red; missing or malformed evidence still fails the final verification job.

Run the acceptance probe from Actions → Verify CI Failure Evidence → Run workflow, enable the confirmation input, or dispatch it with:

gh workflow run failure-evidence.yml \
--ref main \
-f confirm_controlled_failure=true

Before each native matrix run, CI seeds representative stale build and distribution files. It first verifies that normal clean removes only the selected build tree, then that clean with the distribution flag removes both repository-owned trees. It reseeds stale state so the Debug test's fresh configure and the package consumer's fresh export must also remove it. The final verification requires a newly configured cache, public umbrella header, package config, and generated build metadata, so deletion alone cannot produce a false pass.
