Version-controlled plan and quality gates for the Foundation 1.x line.

This page is the source of truth for Foundation 1.x stabilization. Update it in the same commit that changes a task's status or acceptance evidence. Do not maintain a separate progress copy in chat, a spreadsheet, or a Gantt.

Allowed task states are:

State Meaning
NEXT The next task to execute.
TODO Accepted scope, not started.
IN PROGRESS Work exists locally or on a branch but is not accepted.
BLOCKED Cannot continue until the recorded dependency is resolved.
DONE Acceptance criteria passed and evidence is recorded.
DEFERRED Explicitly removed from the current 1.x scope.

Update Rules

  • Keep task IDs stable so commits and conversations can refer to them.
  • Change a task to DONE only after all stated acceptance criteria pass.
  • Record evidence as a commit SHA, CI run, command log, package inspection, consumer build, or hardware-validation record.
  • A successful cross-compilation is not evidence of target execution.
  • A test run that discovers zero tests is not a passing test result.
  • When scope changes, mark the task DEFERRED and explain why; do not delete it.
  • Update the status header and release gates whenever this backlog changes.

Release Gates

Use the gates below before declaring a target SUPPORTED, granting external use, or publishing a release whose scope depends on that evidence:

  • All P0 tasks are DONE; remaining P1 tasks are either DONE or explicitly DEFERRED with a documented limitation.
  • The support matrix matches collected evidence.
  • Required CI is green on the exact release commit.
  • Native Debug and Release tests execute and pass; zero tests is rejected.
  • Release packages contain no Debug artifacts.
  • Separate consumers link the installed packages.
  • Required embedded archive, firmware-link, and hardware evidence exists.
  • Documentation builds and contains no known release contradiction.
  • Qualified legal review has approved the final license, copyright ownership, contribution terms, and intended distribution model.
  • The worktree is clean and the release can be reproduced from a clean clone.
  • Release notes, packages, and checksums are ready before creating the final tag.
